## Live constraints

- **The shared helper is the only place annualization logic may live.** `monthlyIncomeTaxCents`/`monthlyIncomeTaxByCategoryCents` in `packages/engine/src/projection/incomeTax.ts` are called from exactly three sites (`allocationStep.ts`, `fundingDrawStep.ts`, `withdrawal.ts`). Part 2 must upgrade the INTERNALS of these functions (or replace them with YTD-aware equivalents reusing the same call-site shape) — never duplicate the YTD math at the three call sites separately. This is an explicit issue requirement ("Prefer one engine-level helper... so normal monthly taxation and withdrawal gross-up cannot drift apart").
- **`Jurisdiction.computeTaxCents`/`computeTaxByCategoryCents` now take ANNUAL taxable-by-category and return ANNUAL tax/breakdown.** Any new test mock jurisdiction must honor this. `usJurisdiction` (real federal tax) already does.
- **`apportionByWeight`** already exists at `packages/engine/src/money/money.ts:38` (largest-remainder distributor, `(totalCents, weights: readonly [string, number][]) => Map<string, Cents>`) — reuse it for any new per-category apportionment; do not write a second implementation.
- **The reconciliation invariants are unchanged and must keep holding**: `assertPersonTaxBreakdownReconciles` / `assertTaxAttributionReconciles` in `packages/engine/src/projection/waterfallInvariants.ts` — Σ(per-category) === scalar tax, exact to the cent, checked per person before household aggregation.
- **Design worked out for Part 2** (see full reasoning in conversation history / re-derive from the issue's Implementation section, this is the key insight): the per-month **charge** needs `priorYTD` (taxable-by-category before this month) AND `priorTaxPaidYTD` (cumulative tax charged before this month, both scalar and per-category, since telescoping only holds if increments are tracked, not recomputed). But the **gross-up marginal-tax probe** (fundingDrawStep, withdrawal) does NOT need `priorTaxPaidYTD` — inducedTax(draw) = target(priorYTD + thisMonthSoFar + draw) − target(priorYTD + thisMonthSoFar), both at the SAME `monthsElapsed`, so `priorTaxPaidYTD` cancels out of the subtraction. Only `priorYTD` (by owner, by category) and `monthsElapsed` need threading into `fundingDrawStep.ts`/`withdrawal.ts`; only the waterfall's actual charge (`allocationStep.ts`/`waterfall.ts`) needs the full `priorTaxPaidYTD` state too.
- **State to add to `SimState`** (`packages/engine/src/projection/runState.ts`), mirroring `earnedByPersonYear`/`deferredByPersonYear` (keyed `${personId}|${year}`, so a new year naturally starts fresh):
  - cumulative taxable income YTD by category, per person
  - cumulative income tax charged YTD (scalar), per person
  - cumulative income tax charged YTD by category, per person (needed so the monthly per-category INCREMENT — not just the scalar — can be computed by differencing, the same after-minus-before pattern `payrollTaxForPerson` already uses in `waterfall.ts`)
- **`month → calendar-month-within-year` is NOT centralized anywhere** — every existing site (`simulate.ts:152`, `rmd.ts:26,50`, `governmentBenefit.ts:95`, etc.) inlines `startYear + Math.floor(month / 12)` and `month % 12`. `monthsElapsed` (1-indexed, within the current calendar year, INCLUDING this month) = `(month % 12) + 1`. Consider whether this deserves a tiny shared helper or is fine inlined once at the `allocateMonth`/`simulate.ts` call site and threaded down like `ctx.year` already is — the existing codebase's convention favors inlining a one-line formula over a helper module, but do check for drift risk if it ends up needed in 3+ places.
- **`resolveOrderedFundingDraw`/`buildWithdrawalSources`'s injected `computeTaxCents` closures currently take a single `TaxableByCategory` map and are reused across MULTIPLE owners within one call** (a mixed-order draw can walk sources owned by different people). Making them YTD-aware requires the closure to know WHICH owner it's pricing — i.e. the function signature threaded through `resolveOrderedFundingDraw`/`buildWithdrawalSources`/`estimateNetIncome` likely needs to become owner-aware (e.g. `(ownerId, taxable) => Cents` instead of `(taxable) => Cents`), OR the caller constructs a fresh per-owner-bound closure before each source is priced. Check call sites carefully — `fundingDrawStep.ts`'s `resolveOrderedFundingDraw` builds ONE `computeTaxCents` closure for the whole ordered-source walk today.
