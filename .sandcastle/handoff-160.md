## Part B summary (household funding split/cascade)

`projection/waterfall.ts`:
- `proportionalSplit(totalCents, personIds, weightOf)` — the shared cumulative-rounding helper both the income split and the new asset-fallback split use.
- `splitSharedObligation`'s zero-income branch now splits by `WaterfallInput.eligibleAssetsCentsByPerson` (a new optional pure seam, wired in `allocationStep.ts: planMonthAllocation` as "sum of `state.accounts` this person owns") instead of dumping the whole obligation as shortfall.
- `WaterfallResult.obligationShortfallByPersonCents: ReadonlyMap<string, Cents>` — a **separate, independently-floored** (not cumulative-rounded) re-split of the already-finalized `shortfallCents`, by the same weight (income or assets). **Load-bearing distinction, do not "simplify" it back to reading off `shareByPerson` directly**: `shareByPerson`'s cumulative rounding always hands the exact remainder cent to whichever person is LAST in `personIds` array order, which is positionally fixed (`[p1, p2]`) and does not track economic ROLE. `estateSettlement.partners.test.ts`'s "produces the identical household ... whichever of them dies first" mirror test caught this the first time — two people with tied take-home must get IDENTICAL (not off-by-one-cent) decumulation targets regardless of which raw id plays which role, or the run diverges by a few cents in month 1 and that compounds into real dollars by the horizon. If you touch this again, rerun `estateSettlement.partners.test.ts` specifically.

`projection/withdrawal.ts`:
- `buildWithdrawalSources` takes a new optional last param `byPersonCents?: ReadonlyMap<string, Cents>` (from `obligationShortfallByPersonCents` above, threaded through `allocationStep.ts: projectObligationShortfallCents` → `simulate.ts`). Two or fewer people with a positive share ⇒ behaves byte-identically to before this param existed (single-earner households are the overwhelming majority of the test suite; this is why it's safe).
- With 2+ people: each person's target is **independently FLOORED** against `need` (the gap after the shared liquid buffer) — same reasoning as above, never cumulative, never rounded up, so tied weights are exactly tied and the sum never overshoots `need` (no clamp-order tie-break needed either). Drains that person's OWN accounts (liquidation-ordered, excluding the shared liquid account) first; whatever's left (their own accounts insufficient, or an unattributed residual) falls through to the **existing, unchanged pooled pass** — this is the cross-partner coverage.
- The shared liquid buffer (`state.liquidAccount`, still the single global one — `runState.ts:319`) is deliberately UNCHANGED and drained first regardless of person, same as before. Only the INVESTMENT liquidation became person-aware. A genuinely per-person liquid buffer was judged out of scope/too risky for this pass — see "Not done" below.

Tests: `ledger/events.partnerAccounts.test.ts` (Part A), new cases in `projection/withdrawal.test.ts` (Part B — own-account draw, cross-covering, never-negative, pooled-fallback-when-no-hint, asset-proportional split, one end-to-end `simulateHousehold` case).

## Part C — person-specific obligations (not started; why it's separate from Part B)

The issue: "Person-specific obligations should remain assigned entirely to that person." Investigated but not implemented, because:

- **Ordinary expenses have no real per-person authoring surface today.** `compile/projectionBase.ts`'s `compileExpenseBudgetLines(budgetLines, PRIMARY_PERSON_ID, ...)` tags EVERY budget-line expense series `ownerId: PRIMARY_PERSON_ID`, always, regardless of household composition — there is no UI/API path to author a budget line as "this is specifically the partner's." So "personal" only has real, unambiguous data for LIABILITIES (a loan/mortgage/credit card is authored with a genuine `ownerId` — see `LoanEvent.ownerId`).
- **`FinancialObligation` carries no owner at all today.** `projection/financialObligation.ts: buildObligations` drops `liability.ownerId` and `s.ownerId` on the floor when constructing obligations — a `FinancialObligation.ownerId` field would need adding, populated (at minimum) from `liability.ownerId` for `sourceKind: "liability"` entries.
- **The real work is a new waterfall STEP, not a filter.** `automaticFundingCents` (`simulate.ts:370`) is one scalar obligations total, read at THREE OTHER reconciliation points in `simulate.ts` (lines ~530, ~594) with exact-sum invariants. Splitting it into "personal, charged against the owner's own take-home before the shared split runs" + "shared" requires a new step between `computeTakeHome` and `splitSharedObligation` in `waterfall.ts` (subtract each person's personal debt from their OWN take-home first, track what THEY specifically couldn't cover, THEN run the existing shared split on what's left) — not a small change, and one with no existing test coverage to validate the new semantics against (unlike Part B's asset-fallback, which slotted into an already-tested seam).
- Given the risk of silently breaking one of `simulate.ts`'s reconciliation assertions (the kind of thing `estateSettlement.partners.test.ts` caught for Part B, except there is no equivalent test yet for this), this was judged too large to rush. A fresh agent doing this should: (1) add `ownerId?: PersonId` to `FinancialObligation`, sourced from `liability.ownerId` only (leave expense series alone — no real personal-expense data exists to source from); (2) in `simulate.ts`, split `obligations` into `personalByPerson` (has an ownerId) vs the rest before computing `automaticFundingCents`, and re-derive every downstream sum from the SAME split rather than re-summing separately; (3) add a `WaterfallInput.personalObligationCentsByPerson?: (pid) => Cents` seam, consumed in a new step right after `computeTakeHome` inside `runWaterfall`, before `splitSharedObligation` runs on the reduced total; (4) fold each person's personal shortfall into `obligationShortfallByPersonCents` directly (no proportional split needed — it's already known whose it is); (5) write the reconciliation test FIRST (a two-partner household, one liability owned by the partner alone, checked against a single-earner-equivalent control) before touching `simulate.ts`'s existing sums.
